# Zylo Phase 3 Implementation Plan — ZyloRoom video on LiveKit (up to 20) + ZyloChat

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** People seated in a ZyloRoom see and hear each other over LiveKit, with their own mic and camera under their control and a human text chat (ZyloChat) that reaches seated members only.

**Architecture:** The server gains `lib/livekit.js` — a `createLivekit()` factory that returns `null` when the LiveKit env vars are missing (exactly like `createDb(url)` already does for Postgres) and otherwise exposes `ensureRoom` and `mintToken`. A new REST route `GET /api/meetings/:id/livekit-token` mints a token only for a caller who currently holds a seat in the in-memory `seats.js` map that the Socket.IO layer maintains, so authorization is the same single source of truth for media as it already is for admission. ZyloChat is one more handler inside the existing `room.js`, broadcast to `roomChannel(meetingId)` — the Socket.IO room that only seated members are joined to. On the web, `lib/use-livekit-room.ts` owns the `Room` object: it fetches the token, connects with `autoSubscribe: false`, always subscribes to audio, and subscribes to video for only the five most-recently-active people. `components/video-stage.tsx` renders the grid from the authoritative `room:presence` roster and overlays LiveKit tracks onto it; `components/control-bar.tsx` replaces the Phase 2 footer; `components/chat-panel.tsx` is the ZyloChat side panel. No screen share, no host controls, no AI.

**Tech Stack:** `livekit-server-sdk` 2.19.0 (server, CommonJS), `livekit-client` 2.22.3 and `@livekit/components-react` 2.9.24 (web), local `livekit-server --dev` 1.13.7 via Homebrew, Express 5.2, socket.io 4.8.3, pg 8, Postgres 16, `node:test`, Next.js 16.3.5, React 19.2.8, Tailwind v4, shadcn/ui (radix base, nova preset), Lucide, sonner, `@clerk/express` 2.1.67, `@clerk/nextjs` 7.9.2.

**Spec:** `docs/superpowers/specs/2026-09-14-zylo-design.md` — sections "Phase 3 — ZyloRoom video on LiveKit (up to 20) + ZyloChat", "Authentication" (LiveKit tokens), "Authorization", "Contracts", "Repo layout", and "LiveKit free tier vs 15–20 people".

## Deviations from the spec

These two decisions differ from what `2026-09-14-zylo-design.md` says. **Both need the user's sign-off before Task 1 starts.**

1. **No automated test runs against a real `livekit-server`.** The spec's Phase 3 step 1 opens with "Run `livekit-server --dev`", which reads as though the dev server underpins this phase's verification. This plan instead tests the token route by injecting a fake LiveKit client into `createApp({ db, auth, livekit })` — the same injection `createApp` already uses for `db` and `auth` — and separately verifies a *real* minted JWT with the SDK's own `TokenVerifier` (no network). Everything that genuinely needs a media server — 3–4 browsers seeing and hearing each other, the 21st connection being refused, leaving and rejoining within 30 s — stays in the manual acceptance pass in Task 7. Rationale: making `npm --prefix server test` depend on a Homebrew binary and a running WebRTC server on every machine and in CI buys one happy-path assertion and costs every future test run. This mirrors the Phase 2 decision to skip `scripts/race-check.js`. Flag this testing-scope cut for approval.

2. **The "5 most-recent speakers" list is seeded with everyone already in the room, in join order.** The spec says "live video for the 5 most-recent speakers". Read literally, a room where nobody has spoken yet has no recent speakers, so a 3-person ZyloRoom would show three avatars and no video until somebody made a sound — which looks broken. This plan keeps one ordered list of identities: active speakers are moved to the front on `RoomEvent.ActiveSpeakersChanged`, and anyone who joins or publishes is appended to the back. The first five *remote* identities in that list get live video. In a room of ≤ 6 everyone is visible immediately; in a larger room it converges on the spec's behaviour within seconds. Flag this behavioural interpretation for approval, since a reviewer could reasonably insist on strict "only people who have actually spoken get video".

### Refinements inside the spec's contract (no sign-off needed)

Recorded so an executor does not "correct" them back.

- **Filenames are kebab-case.** The spec's repo layout says `web/components/VideoStage.tsx`, `ControlBar.tsx`, `ChatPanel.tsx` and `web/lib/useLiveKitRoom.ts`. Phases 1 and 2 already established kebab-case for every web file (`pre-join.tsx`, `room-shell.tsx`, `people-panel.tsx`, `use-meeting.ts`), so this phase writes `video-stage.tsx`, `control-bar.tsx`, `chat-panel.tsx` and `use-livekit-room.ts`. The exported component names still match the spec (`VideoStage`, `ControlBar`, `ChatPanel`, `useLiveKitRoom`).
- **`GET /health` gains `livekit`.** The spec's Contracts table already says `{ ok, db, livekit }`; Phase 1 shipped `{ ok, db }`. Task 1 closes that gap. `livekit` reports whether the env is configured, not whether the media server answers — a health endpoint should not make an unbounded outbound call on every probe.
- **The token route checks in this order: 400 bad code → 503 LiveKit not configured → 403 no seat → 404 unknown meeting → 403 removed.** A server that cannot mint any token at all should say so before it starts judging the caller.
- **ZyloChat has no history.** The spec's defaults say "ZyloChat messages are not stored", so somebody admitted late sees only what arrives after they sit down. Nothing is persisted and nothing is replayed.
- **No unread badge on the ZyloChat button.** Not in the spec, and it would mean tracking read state for a panel that is visible by default on desktop. Skipped.
- **Env var names are LiveKit's own conventions:** `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`, server-side only. The browser never needs its own LiveKit URL because the token route returns `{ token, url }` together.
- **A token is fetched per connection attempt, not once per meeting.** Tokens live 10 minutes per the spec, and LiveKit has no refresh API. When the client SDK gives up reconnecting it emits `RoomEvent.Disconnected`; the hook then re-runs its connect effect, which fetches a fresh token. This is what makes a 10-minute TTL safe in a one-hour meeting.

## Global Constraints

Every task's requirements implicitly include this section.

- **Node:** ≥ 22. **Server:** CommonJS, runs with `node server.js`, no build step. Tests are `node --test --test-concurrency=1 test/*.test.js`.
- **Web:** Next.js 16.3.5 App Router + React 19.2.8 + TypeScript + Tailwind v4 + shadcn/ui (radix base, nova preset). No `src/` directory. Middleware file is `web/proxy.ts`.
- **Auth packages:** `@clerk/express` 2.1.67 (server) and `@clerk/nextjs` 7.9.2 (web). **Never** `@clerk/clerk-sdk-node` or `@clerk/backend`.
- **Media packages:** `livekit-server-sdk` 2.19.0 (server), `livekit-client` 2.22.3 and `@livekit/components-react` 2.9.24 (web). These two web packages are **not** version-matched to each other; `@livekit/components-react` 2.9.24 declares `peerDependencies: { "livekit-client": "^2.20.1" }`, which 2.22.3 satisfies. Its `@livekit/krisp-noise-filter` peer is marked optional and is not installed. Do **not** import `@livekit/components-styles`.
- **Identity:** always from the verified Clerk token plus the `users` table, or from the seat record. Never read a name or user id from a socket payload or request body.
- **Authorization is enforced server-side.** Hiding a UI control is never a permission check. A LiveKit token is minted only for a user who currently holds a seat and is not removed; clients never receive `roomAdmin`.
- **LiveKit token grants, exactly:** `identity = userId`, `ttl = 10m`, `roomJoin`, `canSubscribe`, `canPublish`, `canPublishSources: [TrackSource.CAMERA, TrackSource.MICROPHONE]`. Nothing else.
- **Missing env or dependency:** loud warning plus a real error (`503`). Never a crash, never fabricated data, never a mocked success. This now covers `LIVEKIT_URL` / `LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET` alongside `DATABASE_URL` and the Clerk keys.
- **Brand names** (Zylo, ZyloMeet, ZyloCall, ZyloRoom, ZyloLive, ZyloChat) come only from `web/lib/brand.ts`. `brand.live` is **ZyloLive = screen share, which is Phase 4** — plain camera video has no brand name of its own, it is just being in ZyloRoom. `brand.chat` is this phase's human chat. Code identifiers, socket event names and routes stay technical (`chat:message`, `/api/meetings/:id/livekit-token`).
- **Design system — "Soft UI Evolution":** primary indigo `#6366F1`, success `#059669`, warning `#D97706`, destructive `#DC2626`, Plus Jakarta Sans. Colors only through the CSS tokens in `web/app/globals.css` (`border-success`, `text-destructive`, …) — no raw hex in components. **ZyloRoom is always dark** (`.dark` tokens) regardless of the dashboard's light/dark setting.
- **UI quality:** Lucide icons only, no emoji. Every icon-only button has an `aria-label` and a `Tooltip`. Touch targets ≥ 44px on primary actions. Transitions 150–300 ms. Respect `prefers-reduced-motion`.
- **Breakpoints:** 375 / 768 / 1024 / 1440, no horizontal scroll. The side panel is docked at ≥ 1024px and behind a `Sheet` below it.
- **Seat rule:** `max_participants` includes the host, range 2–20, default 20. **The host's seat is always reserved**, so non-host users take at most `max − 1` seats. LiveKit's `maxParticipants` is the second, independent cap.
- **ponytail is active at level full:** laziest correct solution, no speculative abstractions, reuse before writing. Mark any deliberate corner-cut with a `ponytail:` comment naming the ceiling and the upgrade path.
- **Verify the API before coding against it.** LiveKit's SDK surface changes between minor versions. Where a step carries a **VERIFY** note, read the installed `.d.ts` in `node_modules` before writing the line it points at — do not trust memory.
- **Do not build in this phase:** ZyloLive / screen share, `host:kick`, `host:mute`, `host:set-screen-policy`, `host:stop-share`, `host:end-meeting`, AI in ZyloChat. Those are Phases 4 and 6 and must not be stubbed in — no dead buttons, no unused event names, no `TODO: Phase 4` handlers.

- [ ] **Step 3: Write `server/lib/livekit.js`**

```js
const { AccessToken, RoomServiceClient, TrackSource } = require('livekit-server-sdk');

// The spec's token rules: a seat-holder gets 10 minutes, camera and microphone,
// and never room admin.
const TOKEN_TTL = '10m';
// Keep the room alive for 5 minutes with nobody in it, so the last person to
// leave and come straight back does not land in a brand-new room.
const EMPTY_TIMEOUT = 300;

/**
 * Returns null when LiveKit is not configured, exactly like createDb(url) does
 * for Postgres. Callers turn that null into a loud warning plus a 503; nothing
 * anywhere fabricates a token.
 */
function createLivekit({
  url = process.env.LIVEKIT_URL,
  apiKey = process.env.LIVEKIT_API_KEY,
  apiSecret = process.env.LIVEKIT_API_SECRET,
} = {}) {
  if (!url || !apiKey || !apiSecret) return null;

  // RoomServiceClient talks Twirp over http; it rewrites a ws:// host itself, so
  // the same LIVEKIT_URL serves both the browser and this client.
  const rooms = new RoomServiceClient(url, apiKey, apiSecret);

  // ponytail: per-process memo of rooms we have already created, matching
  // auth.js's syncedUsers. A restart re-creates them, which LiveKit accepts.
  // Move to Redis alongside seats.js if a second server instance ever appears.
  const created = new Set();

  /**
   * LiveKit would auto-create the room on first join, but then it would have no
   * participant cap. Creating it first is what makes maxParticipants the second,
   * independent cap the spec asks for.
   */
  async function ensureRoom(meetingId, maxParticipants) {
    if (created.has(meetingId)) return;
    await rooms.createRoom({ name: meetingId, maxParticipants, emptyTimeout: EMPTY_TIMEOUT });
    created.add(meetingId);
  }

  async function mintToken({ meetingId, userId, name }) {
    const token = new AccessToken(apiKey, apiSecret, { identity: userId, name, ttl: TOKEN_TTL });
    token.addGrant({
      room: meetingId,
      roomJoin: true,
      canSubscribe: true,
      canPublish: true,
      canPublishSources: [TrackSource.CAMERA, TrackSource.MICROPHONE],
    });
    return token.toJwt();
  }

  return { url, ensureRoom, mintToken };
}

module.exports = { createLivekit };
```

```ts
'use client';

import { useCallback, useEffect, useRef, useState } from 'react';
import { DisconnectReason, Room, RoomEvent, type RemoteParticipant } from 'livekit-client';
import { toast } from 'sonner';
import { useApi } from '@/lib/api';
import { brand } from '@/lib/brand';

/**
 * Live video for this many most-recently-active remote people; everyone else is
 * audio plus an avatar. This is the whole cost story for a 20-person ZyloRoom.
 */
const LIVE_VIDEO_LIMIT = 5;

export type MediaPrefs = { micOn: boolean; camOn: boolean };

/**
 * Connects to the meeting's LiveKit room, starting from the mic/camera choice
 * made on the pre-join screen. Pass `null` until the server has actually seated
 * this user — the token route refuses anyone without a seat, and asking early
 * would just produce a 403 toast.
 */
export function useLiveKitRoom(meetingId: string | null, prefs: MediaPrefs) {
  const api = useApi();
  const [room, setRoom] = useState<Room | null>(null);
  const [micOn, setMicOn] = useState(false);
  const [camOn, setCamOn] = useState(false);
  // Bumped when the client SDK gives up reconnecting. That re-runs the connect
  // effect, which fetches a fresh token — they only last 10 minutes, and LiveKit
  // has no refresh API.
  const [attempt, setAttempt] = useState(0);

  const prefsRef = useRef(prefs);
  // Deliberately no dependency array: this keeps the ref current without making
  // the pre-join prefs a dependency of the connect effect, which would reconnect
  // the room every time the parent re-renders.
  useEffect(() => {
    prefsRef.current = prefs;
  });

  useEffect(() => {
    if (!meetingId) return;

    const next = new Room({ adaptiveStream: true, dynacast: true });
    // Identities, most-recently-active first. Plain local state, not React state:
    // nothing renders from it, it only drives setSubscribed calls.
    let order: string[] = [];
    let cancelled = false;

    const apply = () => {
      const live = new Set(
        order.filter((id) => next.remoteParticipants.has(id)).slice(0, LIVE_VIDEO_LIMIT),
      );
      next.remoteParticipants.forEach((participant) => {
        // You always hear everyone, whether or not you can see them.
        participant.audioTrackPublications.forEach((pub) => pub.setSubscribed(true));
        const wanted = live.has(participant.identity);
        participant.videoTrackPublications.forEach((pub) => pub.setSubscribed(wanted));
      });
    };

    // A new arrival goes to the back of the list, so they get video only while
    // the room is small enough — or as soon as they speak.
    const seen = (identity: string) => {
      if (!order.includes(identity)) order.push(identity);
      apply();
    };
    const promote = (identities: string[]) => {
      order = [...identities, ...order.filter((id) => !identities.includes(id))];
      apply();
    };

    next.on(RoomEvent.ActiveSpeakersChanged, (speakers) => promote(speakers.map((s) => s.identity)));
    next.on(RoomEvent.ParticipantConnected, (p: RemoteParticipant) => seen(p.identity));
    next.on(RoomEvent.TrackPublished, (_publication, p: RemoteParticipant) => seen(p.identity));
    next.on(RoomEvent.ParticipantDisconnected, (p: RemoteParticipant) => {
      order = order.filter((id) => id !== p.identity);
      apply();
    });
    next.on(RoomEvent.Disconnected, (reason) => {
      if (cancelled || reason === DisconnectReason.CLIENT_INITIATED) return;
      setAttempt((n) => n + 1);
    });

    api<{ token: string; url: string }>(`/meetings/${meetingId}/livekit-token`)
      .then(({ token, url }) => next.connect(url, token, { autoSubscribe: false }))
      .then(() => {
        if (cancelled) return;
        next.remoteParticipants.forEach((p) => order.push(p.identity));
        apply();
        setRoom(next);
        setMicOn(prefsRef.current.micOn);
        setCamOn(prefsRef.current.camOn);
      })
      .catch((err: unknown) => {
        if (cancelled) return;
        toast.error(err instanceof Error ? err.message : `Could not connect to ${brand.room} video.`);
      });

    return () => {
      cancelled = true;
      setRoom(null);
      next.disconnect().catch(() => {});
    };
  }, [meetingId, attempt, api]);

  // One effect per device: it publishes the pre-join choice on connect and every
  // later toggle through exactly the same path.
  useEffect(() => {
    if (!room) return;
    room.localParticipant.setMicrophoneEnabled(micOn).catch(() => {
      toast.error('Your microphone is unavailable. Check your browser’s site permissions.');
      setMicOn(false);
    });
  }, [room, micOn]);

  useEffect(() => {
    if (!room) return;
    room.localParticipant.setCameraEnabled(camOn).catch(() => {
      toast.error('Your camera is unavailable. Check your browser’s site permissions.');
      setCamOn(false);
    });
  }, [room, camOn]);

  const toggleMic = useCallback(() => setMicOn((on) => !on), []);
  const toggleCam = useCallback(() => setCamOn((on) => !on), []);

  return { room, micOn, camOn, toggleMic, toggleCam };
}
```

**VERIFY before writing this file** — read these in `web/node_modules/livekit-client/dist/src/`:
- `room/Room.d.ts`: `remoteParticipants: Map<string, RemoteParticipant>` is documented as "map of identity: [[RemoteParticipant]]" — keyed by **identity**, not sid. `connect: (url, token, opts?: RoomConnectOptions) => Promise<void>` and `disconnect: (stopTracks?) => Promise<void>` are properties, so they are safe to pass around.
- `options.d.ts`: `adaptiveStream` and `dynacast` live on `RoomOptions` (the constructor); `autoSubscribe` lives on `RoomConnectOptions` (the `connect` call). They are **not** interchangeable.
- `room/participant/RemoteParticipant.d.ts`: `audioTrackPublications` and `videoTrackPublications` are `Map<string, RemoteTrackPublication>`, and `RemoteTrackPublication.setSubscribed(subscribed: boolean): void` is synchronous.

```tsx
  person,
  micRef,
  camRef,
}: {
  person: Person;
  micRef: TrackReferenceOrPlaceholder;
  camRef?: TrackReference;

        <VideoTrack
          trackRef={camRef}

function LiveGrid({ people }: { people: Person[] }) {
  // Only subscribed cameras: the hook decides who those five are, and this just
  // renders whatever actually arrived.
  const cams = useTracks([Track.Source.Camera], { onlySubscribed: true });
  // Placeholders included, so somebody with their mic off still has a reference
  // to read isSpeaking / isMuted from.
  const mics = useTracks([{ source: Track.Source.Microphone, withPlaceholder: true }], {
    onlySubscribed: false,

      {/* Audio is always on for everyone, whether or not their tile shows video. */}
      <RoomAudioRenderer />
      <div className={GRID}>
        {people.map((person) => {

          const camRef = cams.find((c) => c.participant.identity === person.userId);
          return micRef ? (
            <LiveTile key={person.userId} person={person} micRef={micRef} camRef={camRef} />
          ) : (
            <Tile key={person.userId} person={person} speaking={false} muted={false} />
          );
        })}
      </div>
    </>

      </div>
    );

  return (
    <RoomContext.Provider value={room}>
      <LiveGrid people={people} />
    </RoomContext.Provider>
  );
}
```

```tsx
  }, [messages.length]);

  function send() {
    const text = draft.trim();
    if (!text) return;
    onSend(text);
    setDraft('');
  }

  return (
    <div className="flex h-full min-h-0 flex-col gap-3 rounded-2xl border border-border bg-card p-4">
      <ScrollArea className="min-h-0 flex-1">
        <div className="pr-3">
          {messages.length === 0 ? (
            <p className="py-6 text-center text-sm text-muted-foreground">
              No messages yet. Everyone in this {brand.room} sees what you send here.
            </p>
          ) : (
            <ul className="space-y-3">
              {messages.map((message, index) => (
                <li key={`${message.ts}-${index}`} className="space-y-1">
                  <p className="flex items-baseline gap-2 text-xs text-muted-foreground">
                    <span className="font-semibold text-foreground">
                      {message.userId === selfId ? 'You' : message.name}
                    </span>
                    <time dateTime={new Date(message.ts).toISOString()} className="tabular-nums">
                      {TIME.format(message.ts)}
                    </time>
                  </p>
                  <p className="text-sm break-words whitespace-pre-wrap">{message.text}</p>
                </li>
              ))}
            </ul>
          )}
          <div ref={endRef} />
        </div>
      </ScrollArea>

      <form
        className="flex items-end gap-2"
        onSubmit={(event) => {
          event.preventDefault();
          send();
        }}
      >
        <Textarea
          value={draft}
          onChange={(event) => setDraft(event.target.value)}
          onKeyDown={(event) => {
            // Enter sends, Shift+Enter starts a new line — what people expect
            // from every other meeting chat.
            if (event.key === 'Enter' && !event.shiftKey) {
              event.preventDefault();
              send();
            }
          }}
          maxLength={MAX_CHARS}
          rows={2}
          aria-label={`Message everyone in this ${brand.room}`}
          placeholder={`Message ${brand.room}…`}
          className="min-h-11 resize-none"
        />
        <Button type="submit" size="icon" className="size-11 shrink-0" aria-label="Send message" disabled={!draft.trim()}>
          <SendHorizontal className="size-5" />
        </Button>
      </form>
    </div>
  );
}
```

`scrollIntoView({ block: 'nearest' })` keeps the scroll inside the `ScrollArea` viewport instead of dragging the whole page. Confirm that behaviour by eye in Step 5.
