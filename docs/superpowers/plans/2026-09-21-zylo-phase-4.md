# Zylo Phase 4 Implementation Plan — Host controls + ZyloLive (screen share)

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The host can mute, stop a ZyloLive share, kick (for the rest of the meeting) and end the meeting for everyone; any seated person can present their screen with ZyloLive, one at a time, under the host's policy; and losing a seat — by any path — also ends the LiveKit media session, so a still-valid token can no longer keep anyone in the room.

**Architecture:** Every enforcement call to LiveKit's server API stays in `server/lib/livekit.js`, which gains `evict`, `endRoom`, `grantScreenShare`, `revokeScreenShare`, `muteMic` and `receiveWebhook`. An opt-in live test drives a real Node participant (`@livekit/rtc-node`, server devDependency) to answer "does revoking the screen-share source unpublish the track?" before anything relies on the answer. `server/lib/room.js` routes every seat release through one `freeSeat()` that evicts from LiveKit, and a signed `participant_joined` webhook (`server/lib/webhook.js`, mounted outside `/api` and before `express.json()`) evicts any identity that joins without a seat. The ZyloLive lock lives in the pure `seats.js`, owned by a **socket** (the page that started the share) and taken with a synchronous check-and-set. On the web, capture starts in exactly one place — an effect keyed on a grant *counter* — so no reconnect or re-render can ever re-open the screen picker; everything that can be wrong (stage layout, denial copy, host menu contents) is a zero-import pure module under `web/lib/` with `node --test` coverage.

**Tech Stack:** `livekit-server-sdk` 2.19.0 (server, CommonJS), `livekit-client` 2.22.3 (web, **only**), `@livekit/rtc-node` ^1.1.0 (**server devDependency**, opt-in live test and one manual drill only), local `livekit-server` 1.13.7 via Homebrew, Express 5.2, socket.io 4.8.3, pg 8, Postgres 16, `node:test`, Next.js 16.3.5, React 19.2.8, Tailwind v4, shadcn/ui (radix base), Lucide 1.46, sonner, Clerk.

**Spec:** `docs/superpowers/specs/2026-09-14-zylo-design.md` (in the worktree) — "Phase 4 — Host controls + ZyloLive", "ZyloLive — screen share (one at a time)", "Authorization", "Seats, admission and the 'one seat left' race", "Contracts" (the Socket.IO table), "Authentication" (LiveKit tokens), "Page layouts" (ZyloRoom), "Defaults chosen". ## Deviations from the spec

Both need the user's sign-off before Task 1 starts.

**1. The ZyloLive lock belongs to the page that started the share, not only to the seat.**
The spec releases the lock when "the sharer stops, `track.onended` fires, the host stops it, or the sharer's seat is released". Read literally, a sharer who closes their tab keeps the lock for the 30-second seat grace — yet the acceptance list says "The sharer closes their tab → the lock frees", and a new page for the same person (reload, second tab) would see itself named as the sharer. This plan stores the lock as `{ userId, socketId }` and additionally releases it:
- the moment the sharer's **socket disconnects** (not 30 s later);
- when **another socket takes over the seat** (second tab, or a reconnect — Socket.IO gives every reconnect a new socket id);
- when the sharer's **LiveKit connection does a full reconnect** (the rebuilt session comes from the camera/microphone-only token, so it cannot carry the share anyway).

Cost, stated plainly: a network blip long enough to drop the socket, or a full LiveKit reconnect, ends a share; the presenter presses ZyloLive again. The alternative — a lock surviving on a page that is gone — is the bug class this phase is most at risk of.

**2. The presenter does not see their own screen on the stage.**
The spec says "the shared screen fills the stage". For viewers it does. For the presenter it would show a picture of their own screen, which — when the shared surface contains the ZyloRoom tab — is an infinite mirror. The presenter's stage shows the banner "ZyloLive · You are presenting", a short placeholder line, and the filmstrip. A reviewer could reasonably want the self-view, so flag it.

### Refinements inside the spec's contract (no sign-off needed)

Recorded so an executor does not "correct" them back.

- **`meeting:removed` and `meeting:ended` are added, exactly as the contract table names them.** On the client both land in the existing `{ status: 'denied', reason: 'removed' | 'ended' }` state and its existing `DENIED_COPY`, through **one** shared terminal handler that also calls `socket.disconnect()` — Phase 3's privacy fix — so no terminal event can forget it. Phase 2's `meeting:denied { reason: 'ended' }` to queued users when the last seat empties is unchanged.
- **`host:stop-share` carries `{ userId }`.** The spec gives no payload. Without one, a host clicking "Stop ZyloLive" on Priya's row after Priya stopped and Raj started would end Raj's share. The server releases only if that person holds the lock.
- **`screen:denied` reasons are `busy` (with `sharerName`), `host_only`, `unavailable`.** The spec names `busy` and implies `host_only` through its toast "Only the host can use ZyloLive". `unavailable` covers LiveKit being unconfigured or refusing the grant — a real failure the user must be told about.
- **`screen:request` and `screen:stop` carry no payload.** Who is asking comes from the socket, as with every other event.
- **The grant is `updateParticipant(room, identity, { permission })` with the whole permission.** `UpdateParticipantOptions.permission` is replaced atomically (its own doc comment). Side effect: `canPublishData`, which the token leaves at LiveKit's default of `true`, becomes `false` after the first update. Zylo publishes no data.
- **Kick writes `removed_at` for anyone ever admitted**, seated or not (`UPDATE … WHERE meeting_id AND user_id`), so someone who left a second before the click is still blocked. The host cannot kick themselves. Kick is offered on the People list; the lobby keeps Deny.
- **Host mute touches only a live, unmuted microphone.** The muted person's mic toggle mirrors the server mute, and they can unmute themselves (spec default 3; "check in Phase 4" is Task 10's manual check).
- **Every server-initiated ending runs DB → socket event → LiveKit call.** The DB first, so a rejoin or token request racing it is already refused. The socket event before LiveKit, so the client tears media down on its removed/ended screen before LiveKit's disconnect reaches it, and never flashes a media error.
- **The web hook does not auto-retry on `PARTICIPANT_REMOVED` or `ROOM_DELETED`.** A retry would fetch a token, get a 403 and flash an error at someone who was just removed. On those two reasons the hook shows the non-blocking banner ("You're no longer connected to the video…", with Try again) — normally invisible, because the socket's terminal screen has already replaced the room.
- **The ZyloLive button is never hidden or disabled by policy or by someone else presenting.** The server answers with the spec's own toasts. It is disabled only until media is connected.
- **A late joiner is sent `screen:state` on admission**, so someone arriving mid-presentation sees it.
- **The screen is captured with audio** (`{ audio: true }`), matching the spec's `SCREEN_SHARE_AUDIO` grant; it plays through the existing `AudioSink` path.
- **The filmstrip is a horizontal row at every width**, scrolling inside itself (`min-w-0` keeps the page from scrolling). **The control bar wraps** below ~560 px: with ZyloLive added it no longer fits one row at 375 px even for a participant.
- **The webhook route is `POST /livekit/webhook`**, outside `/api` (Clerk cannot authenticate LiveKit), mounted before `express.json()` (the signature covers the raw bytes), mounted only when LiveKit is configured (there is no secret to verify with otherwise), and acting only on rooms whose name is a valid meeting code. `livekit.dev.yaml` sits at the repo root and points at `http://127.0.0.1:4000/livekit/webhook`.
- **`room.js` stays one file** (~480 lines after this phase). The five `host:*` handlers and the ZyloLive handlers share `liveMeetings`, `hostGuard`, `on()`, `roomChannel()`, `onSeatFreed()` and the new `freeSeat()` / `releaseScreen()`; a second module would take all of that as a context object. Revisit if Phase 6 adds much more.
- **New socket tests use shared helpers** (`roomHarness`, `seat`, `collect`, `settle`, `recordingLivekit`, `shareScreen`) added to `server/test/helpers.js`; `room.test.js` is untouched.
- **Folded Phase 3 minors** (both in files this phase changes anyway): `sendChat` emits the trimmed text it validated; the `leaving` branch of `meeting-room-flow.tsx` renders a "You left" `Notice` instead of `null`, so a navigation that never lands leaves a recoverable screen, not a blank one — with no new state to reset. The other Phase 3 deferred minors stay deferred.
- **`removeParticipant`'s `revokeTokenTs` is not used.** It would refuse a seatless reconnect at the door instead of evicting it one webhook round trip later, but its support on `livekit-server` 1.13.7 is unverified. Named in a `ponytail:` comment in `webhook.js`.

## Every way a share or a session ends

This phase's biggest risk is a fourth instance of Phase 3's bug class — **media continuing after the user's intent changed** — now involving screen capture. Every path is listed with what does each of the four jobs, and what proves it. An executor who changes any mechanism below must update this table in the same commit.

**Facts this table relies on, read from `web/node_modules/livekit-client/dist/livekit-client.esm.mjs` at planning time (re-check if the version changes):**
- `LocalParticipant.unpublishTrack(track, stopOnUnpublish)` defaults `stopOnUnpublish` to `roomOptions.stopLocalTrackOnUnpublish ?? true` and calls `track.stop()` — so every unpublish, ours or LiveKit's, stops the capture and the browser's indicator goes off.
- A server-side unpublish arrives as `handleLocalTrackUnpublished` → `this.unpublishTrack(track.track)`, which then emits `RoomEvent.LocalTrackUnpublished`.
- `handleTrackEnded` (the browser's own "Stop sharing" ends the `MediaStreamTrack`) calls `unpublishTrack` for `ScreenShare` and `ScreenShareAudio` sources.
- `setTrackEnabled` stops every track it captured if publishing fails; `setScreenShareEnabled(false)` unpublishes `ScreenShare` **and** `ScreenShareAudio`.
- `Room.disconnect(stopTracks = true)` stops every local track.
- A full reconnect emits `RoomEvent.Reconnecting` (`handleRestarting`, and on `Offline`); a resume emits `RoomEvent.SignalReconnecting` instead and keeps the server session.

## Global Constraints

Every task's requirements implicitly include this section.

- **Node:** ≥ 22. **Server:** CommonJS, `node server.js`, no build step. Tests are `node --test --test-concurrency=1 test/*.test.js` — the `--test-concurrency=1` is mandatory (shared Postgres `TRUNCATE` plus module-global seat state).
- **Web:** Next.js 16.3.5 App Router, React 19.2.8, TS strict, Tailwind v4 (CSS-first, **no `tailwind.config.*`**), shadcn/ui. No `src/`. Middleware is `web/proxy.ts`.
- **Media packages:** `livekit-server-sdk` 2.19.0 (server), `livekit-client` 2.22.3 (web). `@livekit/rtc-node` ^1.1.0 is a **server devDependency**, required only inside `server/test/livekit.live.test.js` (and only when `LIVEKIT_URL` is set) and by the manual drill in Task 11 — **never by app code**. Do not install `@livekit/components-react` / `-styles`.
- **One file per boundary:** `server/lib/livekit.js` is the only file that talks to LiveKit's server API. `web/lib/use-livekit-room.ts` is the only web file that imports **values** from `livekit-client` (type-only imports, as `video-stage.tsx` already does, are fine).
- **Identity** always comes from the verified Clerk token, the `users` table, or the seat record — never from a payload. The sharer's name in `screen:denied` comes from the seat.
- **Authorization is server-side.** Hiding a control is never a check. Every `host:*` handler starts with `hostGuard(socket)`.
- **LiveKit token grants are unchanged from Phase 3:** `roomJoin`, `room`, `canSubscribe`, `canPublish`, `canPublishSources: [CAMERA, MICROPHONE]`, `ttl = 10m`, never `roomAdmin`. Screen share is only ever granted at runtime, per participant, by `grantScreenShare`.
- **The ZyloLive lock is taken in one synchronous block** — no `await` between reading the lock and writing it — exactly like `tryTakeSeat`.
- **Every seat release in `room.js` goes through `freeSeat()`.** After Task 3, `grep -n "seats.releaseSeat" server/lib/room.js` must print exactly one line (inside `freeSeat`).
- **Server-initiated endings run DB → socket event → LiveKit call** (see Refinements).
- **Mount order in `app.js` IS the security model.** The webhook is mounted after `cors` and **before** `express.json()`, outside `/api`.
- **Missing config is degraded mode, never a crash.** Without LiveKit: the webhook is not mounted, `screen:request` answers `screen:denied { reason: 'unavailable' }`, and every `livekit?.x()` call is skipped; kick / end / policy still work at the socket and DB level.
- **Error bodies** are `{ error: "<human sentence, capitalised, full stop>" }`. Handlers validate first and return early.
- **Socket handlers** go through the existing `on(socket, event, handler)` wrapper and destructure with a default (`({ userId } = {}) =>`). A malformed payload from an authorized host is silently ignored (the `host:set-admission` precedent), not answered with `error:forbidden`.
- **Per-meeting in-memory state is cleared where meetings end.** The lock lives inside `seats.js`'s per-meeting state, so `seats.clearMeeting` (natural end and End for all) drops it. `liveMeetings.delete` accompanies both.
- **`use-meeting.ts` gets no `socket.on('disconnect', …)` listener.** A transient drop must not tear video down. Terminal events call `socket.disconnect()`; that is not a listener.
- **Lint bites.** `react-hooks/set-state-in-effect`, `refs`, `immutability`, `purity`, `use-memo`, `preserve-manual-memoization` are **errors**. No synchronous `setState` in an effect body; `setState` in socket/RoomEvent/promise callbacks is fine; never mutate state in place; refs are written in effects (the `prefsRef` pattern) and read in effects, callbacks and handlers — never during render.
- **Every tested `web/lib/*.ts` module has zero local imports** (`moduleResolution: bundler` without `allowImportingTsExtensions`; tests import `./x.ts`). Brand names arrive as a parameter.
- **Brand names** come only from `web/lib/brand.ts`. `brand.live` ("ZyloLive") is now in scope. Event names and routes stay technical (`screen:*`, `host:*`).
- **Design:** ZyloRoom is always dark; colors only through tokens (no raw hex, no `bg-black`). ZyloLive banner and badge: `bg-success text-success-foreground`. End for all / Kick: `destructive`. Icon buttons carry `aria-label` + `Tooltip`; targets ≥ 44 px (`size-11` / `size-12`). **Anything that portals re-declares `className="dark"`** — `SheetContent` already does; `DropdownMenuContent` and `AlertDialogContent` in ZyloRoom must too.
- **Verify the SDK before coding against it.** Where a step carries a **VERIFY** note, read the named `.d.ts` (or bundle) in `node_modules` first.
- **Mutation-check every guard.** Each server task ends with a table of guards and the test that must fail without each. Delete the guard, run, watch that test fail, restore it. Say so in the task's review notes.
- **ponytail is active at level full.** Laziest correct solution, reuse before writing, `ponytail:` comments on deliberate ceilings, a `//` comment on every non-obvious decision.
- **Out of scope — must not appear, even as stubs:** Phase 5 (rate limits, graceful shutdown, structured logs, load test, deploy, Redis) and Phases 6–7 (AI in ZyloChat, stuck detection). No dead buttons, no unused event names, no `TODO` handlers.

    // refusing screen recording (macOS), so one line serves both.

    // livekit-client throws DeviceUnsupportedError where getDisplayMedia is missing (phones).
    if (name === 'DeviceUnsupportedError' || name === 'NotSupportedError') return `${live} isn’t available in this browser.`;
    return `${live} couldn’t share your screen. Try again.`;
  }
