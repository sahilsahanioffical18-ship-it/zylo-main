# Zylo Phase 3 Implementation Plan — ZyloRoom video on LiveKit (up to 20) + ZyloChat

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** People seated in a ZyloRoom see and hear each other over LiveKit, with their own mic and camera under their control, a tabbed side panel carrying human ZyloChat, and a defined, visible, tested failure path for every way the media layer can break.

**Architecture:** The server gains `lib/livekit.js` — a `createLivekit()` factory that returns `null` when the LiveKit settings are missing (exactly like `createDb(url)` does for Postgres) and otherwise exposes `url`, `ping`, `ensureRoom` and `mintToken`. One new REST route, `GET /api/meetings/:id/livekit-token`, mints a token only for a caller who currently holds a seat in the in-memory `seats.js` map that the Socket.IO layer maintains — so media authorization has the same single source of truth as admission. ZyloChat is one handler inside the existing `room.js`, broadcast to `roomChannel(meetingId)`, the Socket.IO room only seated members are joined to. On the web, `lib/use-livekit-room.ts` owns the `Room`, fetches the token, connects with `autoSubscribe: false`, subscribes audio for everyone and video for the five most-recently-active, and hands React a plain data snapshot (never the mutable `Room` internals). Everything that can actually be *wrong* — speaker ordering, chat validation, media-error copy — lives in dependency-free pure modules under `web/lib/` with `node --test` coverage. No screen share, no host controls, no AI.

**Tech Stack:** `livekit-server-sdk` 2.19.0 (server, CommonJS), `livekit-client` 2.22.3 (web, **only**), local `livekit-server --dev` via Homebrew, Express 5.2, socket.io 4.8.3, pg 8, Postgres 16, `node:test`, Next.js 16.3.5, React 19.2.8, Tailwind v4, shadcn/ui (radix base), Lucide, sonner, `@clerk/express` 2.1.67, `@clerk/nextjs` 7.9.2.

## Deviations from the spec

Both need the user's sign-off before Task 1 starts.

**1. The web uses `livekit-client` 2.22.3 only. `@livekit/components-react` is not installed.**
The spec says "use `@livekit/components-react` primitives (`VideoTrack`, `RoomAudioRenderer`, `useTracks`) inside our own shadcn-styled tiles". This plan hand-rolls all three:

| Spec primitive | Replacement here |
|---|---|
| `VideoTrack` | `track.attach(el)` in a `useEffect` inside `Tile`, cleaned up with `track.detach(el)` |
| `RoomAudioRenderer` | a `<RemoteAudio>` block in `video-stage.tsx`: one hidden `<audio autoPlay playsInline>` per subscribed remote audio track, keyed by track sid, plus explicit autoplay-policy handling |
| `useTracks` | the hook's own `snapshot()`, driven by the RoomEvents we already listen to |

Rationale: our hook manages subscriptions manually with `autoSubscribe: false`, which fights `useTracks` (it assumes the components-react context owns subscription policy); and it removes a large dependency tree plus React-19 / Next-16-Turbopack compatibility risk on a package that versions independently (2.9.x against a 2.22.x client).

**What we must get right in exchange** — these are the two things `RoomAudioRenderer` was doing for us, and both are called out as explicit steps in Task 8 and Task 10:
- **Every** remote audio track is attached, including tracks published *after* we connect and tracks belonging to people whose video we are not subscribed to. Driven off `RoomEvent.TrackSubscribed` / `TrackUnsubscribed` filtered to `Track.Kind.Audio`, which only ever fires for remote tracks — the local mic is never attached, so no echo.
- **Browser autoplay policy.** `RoomEvent.AudioPlaybackStatusChanged` → when `room.canPlaybackAudio === false`, a persistent `sonner` toast ("Click to turn on sound") whose action calls `room.startAudio()`, dismissed when playback becomes allowed.

**2. The "5 most-recent speakers" list is seeded with everyone already present, in join order.**
Read literally, a room where nobody has spoken yet has no recent speakers, so a fresh 3-person ZyloRoom would show three avatars and no video until somebody made a sound — which looks broken. This plan keeps one ordered list of identities: active speakers move to the front on `RoomEvent.ActiveSpeakersChanged`; anyone who joins or publishes is appended to the back; the first five *present* identities get live video. In a room of ≤ 6 everyone is visible immediately; a larger room converges on the spec's behaviour within seconds. A reviewer could reasonably insist on strict "only people who have actually spoken get video", so flag it.

### Refinements inside the spec's contract (no sign-off needed)

Recorded so an executor does not "correct" them back.

- **Kebab-case filenames.** The spec's layout says `VideoStage.tsx`, `ControlBar.tsx`, `ChatPanel.tsx`, `useLiveKitRoom.ts`. Phases 1–2 established kebab-case for every web file; this phase writes `video-stage.tsx`, `control-bar.tsx`, `chat-panel.tsx`, `use-livekit-room.ts`. Exported names still match the spec. Server files keep the server's camelCase convention: `lib/livekit.js`, `lib/chatRules.js` (sibling of `meetingRules.js`).
- **`GET /health` gains `livekit`, and it means *reachable*, not *configured*.** The spec's contract says `{ ok, db, livekit }` without defining the semantics. `db` in the shipped handler already means reachable (it runs `SELECT 1`), so `livekit` matches it (`listRooms([])`). A `/health` that reports a configured-but-dead LiveKit as healthy is a lie that costs an operator an hour. Ceiling named with a `ponytail:` comment: neither probe has a timeout.
- **Token route status order: 400 → 503 (not configured) → 403 (no seat) → 404 (unknown meeting) → 403 (removed) → 503 (upstream unreachable) → 200.** Justified in Task 4.
- **`ensureRoom` has no memo.** It calls `createRoom` on every token request. A per-process memo goes stale the moment `livekit-server` restarts, and the room it would then skip creating is the one carrying `maxParticipants` — so the memo can silently disable the second participant cap. One extra Twirp round trip per participant per connect is cheaper than that failure mode. Task 3's live test confirms `createRoom` is idempotent; if it is not, the fallback is a narrow "already exists" catch, *not* a memo.
- **ZyloChat has no history and no replay.** The spec's defaults say messages are not stored. Someone admitted late sees only what arrives after they sit down, and the empty state says so.
- **Chat validation failures are silently dropped, not answered with an error event.** `room.js` already has this precedent: `host:set-admission` ignores a bad `mode` with the comment "a malformed payload is a client bug, not an authorization failure". Our composer enforces the same rules the server does, so a rejected message can only come from a bug or a probe; and `use-meeting.ts` has no `error:forbidden` listener at all, so emitting one would be a dead event. `meeting:denied`'s four reasons and the single `error:forbidden` channel stay exactly as Phase 2 left them. The *tests* assert the silence.
- **No unread badge on the ZyloChat button.** It would need read-state tracking for a panel that is docked and visible on desktop, and `react-hooks/set-state-in-effect` is an error in this repo. Add it if the Task 11 acceptance pass shows people missing messages.
- **No elapsed timer in the top bar.** The spec's UI section lists one, but Phase 3's numbered deliverables are VideoStage / ControlBar / ChatPanel. Deferred; `MeetingCard.startedAt` is already available when it is wanted.
- **The People button moves into the control bar and becomes visible at every width.** Phase 2 had it `lg:hidden` because the panel was permanently docked. With a tabbed panel it now switches the docked panel's tab on desktop and opens the `Sheet` below 1024px — matching the spec's "Bottom control bar: Mic, Camera, ZyloLive, ZyloChat, People, Leave". ZyloLive stays out (Phase 4).
- **Env var names are LiveKit's own:** `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`, server-side only. The browser never needs its own LiveKit URL — the token route returns `{ token, url }` together.
- **A token is fetched per connection attempt, not once per meeting.** Tokens live 10 minutes and LiveKit has no refresh API. When the client SDK gives up reconnecting it emits `RoomEvent.Disconnected`; the hook bumps `attempt`, which re-runs the connect effect and fetches a fresh token.
- **Real-LiveKit tests are opt-in** (the user's decision 2): `server/test/livekit.live.test.js` skips itself when `LIVEKIT_URL` is unset, so the default `npm test` stays green with no LiveKit binary. `dotenv` loads only in `server.js`, so tests never see `server/.env` — the env must be exported on the command line, which is exactly what makes the skip the default.
- **Web testing adds no dependencies** (the user's decision 3). Logic that can be wrong is pulled into dependency-free pure modules under `web/lib/` and tested with the existing `node --test lib/*.test.ts`. **Hard constraint discovered:** `web/tsconfig.json` uses `moduleResolution: bundler` *without* `allowImportingTsExtensions`, and `format.test.ts` imports with an explicit `./format.ts`. Therefore **every new tested `web/lib/*.ts` module must have zero local imports** — a source file importing `./brand.ts` would fail `next build`, and importing `./brand` would fail the Node runner. This is why `mediaErrorMessage` takes the product name as a second argument instead of importing `brand`.

## Global Constraints

Every task's requirements implicitly include this section.

- **Node:** ≥ 22. **Server:** CommonJS, `node server.js`, no build step. Tests are `node --test --test-concurrency=1 test/*.test.js` — the `--test-concurrency=1` is mandatory (shared Postgres `TRUNCATE` plus module-global seat state).
- **Web:** Next.js 16.3.5 App Router, React 19.2.8, TS strict, Tailwind v4 (CSS-first, **no `tailwind.config.*` exists**), shadcn/ui. No `src/`. Middleware is `web/proxy.ts`.
- **Media packages:** `livekit-server-sdk` 2.19.0 (server), `livekit-client` 2.22.3 (web). **Do not install `@livekit/components-react` or `@livekit/components-styles`.**
- **Identity** always comes from the verified Clerk token, the `users` table, or the seat record. Never from a socket payload or request body. The LiveKit token's `name` comes from the seat.
- **Authorization is server-side.** Hiding a control is never a check. A token is minted only for a current seat-holder who is not removed. Clients never receive `roomAdmin`.
- **LiveKit token grants, exactly:** `identity = userId`, `ttl = 10m`, `roomJoin`, `canSubscribe`, `canPublish`, `canPublishSources: [TrackSource.CAMERA, TrackSource.MICROPHONE]`, `room = meetingId`. Nothing else.
- **Missing config is degraded mode, never a crash:** a loud `console.warn` at boot plus a real `503` on the affected route. Now covers the three LiveKit vars alongside `DATABASE_URL` and the Clerk keys.
- **Mount order in `app.js` IS the security model.** Anything added under `/api` after `app.use('/api', auth)` is authenticated for free; anything added before it is not. The token route goes in `meetingsRouter`, which is mounted after auth.
- **Error bodies** are `{ error: "<human sentence, capitalised, full stop>" }`. Handlers validate params on the first line and `return res.status(N).json(...)` early. No controller/service layer.
- **Socket handlers** go through the existing `on(socket, event, handler)` async wrapper, destructure payloads with a default (`async ({ text } = {}) => {}`), and call `ack?.(…)` optionally.
- **Any per-meeting in-memory state Phase 3 adds must be cleared in `onSeatFreed`** alongside `seats.clearMeeting` / `liveMeetings.delete`. (Phase 3 adds none — chat is not stored — but the constraint stands and is checked in the Self-Review.)
- **Lint bites.** `eslint-plugin-react-hooks` v7 makes `react-hooks/set-state-in-effect`, `refs`, `immutability`, `purity`, `use-memo`, `preserve-manual-memoization` **errors**. Rules that follow from that: `setState` inside an async callback (socket handler, RoomEvent handler, `.then`) is fine; a *synchronous* `setState` in an effect body is not — use the microtask-deferral idiom from `use-meeting.ts:40` or a justified single-line disable in the `dashboard-view.tsx:39` style. Never mutate a state array in place (`messages.push(...)`, `order.push(...)` on state). `el.srcObject = stream` and `track.attach(el)` inside an effect are the accepted pattern.
- **Brand names** come only from `web/lib/brand.ts`. `brand.chat` is ZyloChat; `brand.live` is ZyloLive = screen share = **Phase 4** and must not appear. Event names and routes stay technical.
- **Design:** ZyloRoom is always dark. Colors only through the CSS tokens in `web/app/globals.css` — no raw hex. Speaking ring is green: `ring-2 ring-success` (`--success: #059669`). Panels `rounded-2xl border border-border bg-card p-4`; tiles `aspect-video rounded-2xl`; circular media buttons `size-12 rounded-full`; counts `tabular-nums`; `flex min-h-dvh flex-col`, never `h-screen`; scrolling flex children get `min-h-0 flex-1 overflow-y-auto`. Lucide only, `aria-label` + `Tooltip` on every icon button, `role="status"` on loading, `role="alert"` on errors, `motion-reduce:animate-none` on spinners.
- **Anything that portals out of the dark subtree must re-declare `className="dark"`** — `SheetContent` already does; new portals must too.
- **Verify the SDK before coding against it.** Where a step carries a **VERIFY** note, read the installed `.d.ts` in `node_modules` first. Do not trust memory.
- **ponytail is active at level full.** Laziest correct solution, reuse before writing, no speculative abstractions. Mark any deliberate corner-cut with a `ponytail:` comment naming the ceiling and the upgrade path. Every non-obvious decision carries a `//` comment explaining *why*.
- **Do not build in this phase, and do not stub:** ZyloLive / screen share, `host:kick`, `host:mute`, `host:set-screen-policy`, `host:stop-share`, `host:end-meeting`, AI chat. No dead buttons, no unused event names, no `TODO: Phase 4` handlers.

## Task 2: `server/lib/livekit.js` — room creation, ping, and token minting

**Goal:** one module that owns every call to LiveKit's server API, returning `null` when unconfigured.

**Files:** NEW `server/lib/livekit.js`, NEW `server/test/livekit.test.js`.

**Produces:**
```js
createLivekit({ url?, apiKey?, apiSecret?, rooms? } = {}) → LivekitClient | null
// defaults read process.env.LIVEKIT_URL / _API_KEY / _API_SECRET
// `rooms` overrides the RoomServiceClient so tests can drive ensureRoom/ping
//  without a media server — the same override shape the other three already use.

LivekitClient = {
  url: string,
  ping(): Promise<void>,                                     // throws when unreachable
  ensureRoom(meetingId: string, maxParticipants: number): Promise<void>,
  mintToken({ meetingId, userId, name }): Promise<string>,
}
```

## Task 4: `seats.seatFor()` and `GET /api/meetings/:id/livekit-token`

### Open question answered: does `seats.js` get `seatFor()`?

**Yes.** Both the token route and the chat handler need the seat's `name`, and today the only way to get it is `seats.listSeats(id).find(s => s.userId === userId)` — which rebuilds the whole roster array to read one field, at two call sites, on the hot path of every chat message. `seatFor(meetingId, userId) → seat | null` matches the existing `hasSeat` / `seatSocketId` naming exactly, makes "authorize and name in one lookup" a single expression, and makes the spec rule "identity comes from the seat record" literally one call. **`hasSeat` is left untouched** — rewriting it in terms of `seatFor` would allocate an object on the join path's hottest check for zero benefit.

```js
function seatFor(meetingId, userId) {
  const seat = meetings.get(meetingId)?.seats.get(userId);
  return seat ? { userId, ...seat } : null;
}
```

### Open question answered: the order of the status checks

| Order | Status | Condition | Why here |
|---|---|---|---|

## Task 6: `chat:message` — ZyloChat on the server

**Goal:** a message from a seated member reaches every seated member of that meeting and nobody else.

**Files:** MODIFY `server/lib/room.js` (one handler, inserted after `meeting:leave`, before `lobby:admit`); append to `server/test/room.test.js`.

**Contract:**
- C→S `chat:message` `{ text }` — max 2,000 chars after trimming.
- S→C `chat:message` `{ userId, name, text, ts }` broadcast to `roomChannel(meetingId)`.
- Silently dropped when: no `socket.data.meetingId`; the sender holds no seat; this socket is not the one the seat points at (a newer tab replaced it); or `validateChatText` returns `null`. No new outbound error event.

**The trap this handler exists to avoid:** `socket.data.meetingId` is set for **waiting/queued** users too (`room.js:179` and `:189`). It is *not* proof of a seat. The handler gates on `seats.seatFor(meetingId, userId)`, and additionally on `seat.socketId === socket.id` so a socket a newer tab replaced cannot still post.

```js
// ZyloChat. roomChannel holds exactly the seated members — a socket joins it only
// inside admit() — so joining it is both the authorization scope and the delivery
// scope. But socket.data.meetingId is also set for people still in the lobby, so
// it proves nothing on its own: the seat lookup is the real check. The name comes
// from the seat, never the payload, so nobody can speak as someone else.
on(socket, 'chat:message', ({ text } = {}) => {
  const { meetingId, userId } = socket.data;
  if (!meetingId) return;
  const seat = seats.seatFor(meetingId, userId);
  if (!seat || seat.socketId !== socket.id) return;
  const clean = validateChatText(text);
  if (!clean) return;   // a client bug or a probe; see host:set-admission above
  io.to(roomChannel(meetingId)).emit('chat:message', { userId, name: seat.name, text: clean, ts: Date.now() });
});
```

**File-size decision:** `room.js` is 298 lines and this adds ~14. It stays one file — splitting chat out would mean a second module re-deriving `roomChannel`, the `on()` wrapper and the seat lookups that live here. Revisit when Phase 4 adds five `host:*` handlers and the ZyloLive lock.

**Test hazard to respect:** the broadcast reaches the sender too, and several existing tests in this file deliberately drain a stale event first with an explanatory comment. Every chat test registers listeners **before** emitting and settles with a fixed `await new Promise(r => setTimeout(r, 60))` before asserting counts — the assertion that something did **not** arrive needs a settle window, not a race.

## Task 8: `web/lib/use-livekit-room.ts` — connect, publish, subscribe, snapshot

**Goal:** one hook owns the `Room`, and hands React plain immutable data plus a defined status for every failure.

**Files:** NEW `web/lib/use-livekit-room.ts`. **This is the only file in `web/` that imports `livekit-client`.**

**Signature:**
```ts
export type MediaPrefs = { micOn: boolean; camOn: boolean };
export type LiveKitStatus = 'idle' | 'connecting' | 'connected' | 'error';

export function useLiveKitRoom(meetingId: string | null, prefs: MediaPrefs): {
  status: LiveKitStatus;
  error: string | null;            // human sentence when status === 'error'
  retry: () => void;               // bumps `attempt`, refetches the token, reconnects
  videoTracks: Map<string, VideoTrack>;        // identity → camera track (local included)
  audioTracks: { sid: string; track: RemoteAudioTrack }[];  // every subscribed remote audio track
  speaking: Set<string>;           // identities LiveKit reports as speaking
  micMuted: Set<string>;           // identities whose mic is absent or muted
  micOn: boolean; camOn: boolean;
  toggleMic: () => void; toggleCam: () => void;
};
```

### Why the hook returns plain data, not the `Room`

LiveKit mutates the `Room` object in place; React has no way to know. Reading `room.remoteParticipants` during a component's render is an unsynchronised external-store read and would put `react-hooks/purity` pressure on every component that did it. Instead one `snapshot()` function runs inside the hook's own event handlers and produces four plain, comparable collections. Every component then takes ordinary props and is renderable with no media server. Cost: a whole-stage re-render per media event — `// ponytail: coarse re-render for a ≤20-tile grid; move to per-tile subscriptions if the grid ever gets expensive.`

### Structure

- **Connect effect**, deps `[meetingId, attempt, api]`. Returns early when `meetingId` is `null`.
  - `new Room({ adaptiveStream: true, dynacast: true })`.
  - `let order: string[] = []` — a plain local, not React state; it drives `setSubscribed` calls only, and using the pure `promote`/`seen` keeps it immutable-by-habit.
  - `apply()`: `const live = videoIdentities(order, next.remoteParticipants.keys())`; for each remote participant subscribe **every** audio publication (`pub.setSubscribed(true)` — this is the `RoomAudioRenderer` obligation) and set each video publication to `live.has(identity)`.
  - Listeners: `ActiveSpeakersChanged` → `order = promote(order, speakers.map(s => s.identity)); apply(); snapshot()`. `ParticipantConnected` / `TrackPublished` → `order = seen(order, identity); apply(); snapshot()`. `TrackSubscribed` / `TrackUnsubscribed` / `TrackMuted` / `TrackUnmuted` / `LocalTrackPublished` / `LocalTrackUnpublished` / `ParticipantDisconnected` → `snapshot()`.
  - `AudioPlaybackStatusChanged` → if `!next.canPlaybackAudio`, `toast.error('Click to turn on sound for this ZyloRoom.', { id: 'lk-audio', duration: Infinity, action: { label: 'Turn on sound', onClick: () => next.startAudio() } })`; otherwise `toast.dismiss('lk-audio')`.
  - `Disconnected(reason)` → ignore when `cancelled` or `reason === DisconnectReason.CLIENT_INITIATED`. Ignore `DUPLICATE_IDENTITY` too — the socket's `meeting:replaced` already owns that screen, and retrying would fight the new tab for the identity. Anything else: `setAttempt(n => n + 1)` once, and if that attempt also fails, `status: 'error'`.
  - `api<{token,url}>('/meetings/' + meetingId + '/livekit-token')` → `next.connect(url, token, { autoSubscribe: false })` → seed `order` from `remoteParticipants`, `apply()`, `snapshot()`, `setStatus('connected')`, then apply `prefsRef.current`.
  - `.catch` → `setStatus('error'); setError(connectErrorMessage(err))`.
  - Cleanup: `cancelled = true; next.removeAllListeners(); next.disconnect().catch(() => {});` and reset the snapshot collections to empty.
- **`prefsRef`** updated by an effect with **no dependency array**, so the pre-join prefs never become a dependency of the connect effect (which would reconnect the room on every parent re-render). Comment says exactly that.
- **Two media effects**, one per device, deps `[status, micOn]` / `[status, camOn]`: `setMicrophoneEnabled(micOn)` / `setCameraEnabled(camOn)`, `.catch(err => { toast.error(mediaErrorMessage(err, brand.product)); setMicOn(false); })`. This is where a device denied or busy **at the LiveKit layer** surfaces — distinct from pre-join, because pre-join stopped its tracks and these are a fresh acquisition.
- `toggleMic` / `toggleCam` are `useCallback` setState-updaters; the effects do the publishing, so the pre-join choice and every later toggle travel the identical code path.

### Open question answered: PreJoin hands nothing to LiveKit — LiveKit re-acquires

`PreJoin` stops every track in its effect cleanup, and `MeetingRoomFlow` swaps it out the moment the user joins, so the preview stream is always destroyed. **Keep it that way.** Reasons:
1. Handing a raw `MediaStreamTrack` to LiveKit means constructing `LocalVideoTrack` / `LocalAudioTrack` by hand and calling `publishTrack` — which takes those tracks *out* of `setCameraEnabled`/`setMicrophoneEnabled`'s management, so every later toggle, device switch and restart-on-mute needs hand-rolling. That is a large amount of machinery for a cosmetic win.
2. The browser's camera permission is already granted for the origin by the time Join is pressed, so the re-acquisition does **not** re-prompt. The visible cost is a camera-light blink of a few hundred milliseconds.
3. We need `NotReadableError` / `NotAllowedError` handling at the LiveKit layer *anyway* (coverage gap 6), so keeping one code path that owns published tracks is strictly simpler than two.
4. ponytail: zero new code versus a track-handoff layer.

What **does** change: `MeetingRoomFlow` stops discarding `prefs`.

### Open question answered: where the LiveKit lifecycle is guaranteed to tear down (coverage gap 7)

`useLiveKitRoom` is called **in `meeting-room-flow.tsx`**, with its meeting id driven by the same expression that decides which screen renders:

```tsx
const [joined, setJoined] = useState<{ meeting: MeetingCard; prefs: MediaPrefs } | null>(null);
const { state, lobby, admission, messages, leave, sendChat, … } = useMeeting(joined ? code : null);
// One expression decides both "which screen" and "is LiveKit connected", so they
// can never disagree. Seat lost for any reason -> this flips to null -> the connect
// effect's cleanup runs -> room.disconnect().
const media = useLiveKitRoom(state.status === 'admitted' ? code : null, joined?.prefs ?? MEDIA_OFF);
```
(`MEDIA_OFF` is a module-level frozen constant, so no allocation per render.)

That single expression is the guarantee, and it covers every seat-loss path:

| Path | What flips it | Result |
|---|---|---|
| Explicit Leave | `handleLeave()` sets `joined = null` | both hooks tear down; `leave()` already told the server first |
| `meeting:replaced` (second tab) | `state.status` → `'replaced'` | LiveKit disconnects. **And** LiveKit independently evicts the older participant for a duplicate `identity`, so both layers agree — **VERIFY** `DisconnectReason.DUPLICATE_IDENTITY` and make sure the hook does not retry on it |
| `meeting:denied` (kick in Phase 4, ended, removed) | `state.status` → `'denied'` | LiveKit disconnects |
| `connect_error` on the socket | `state.status` → `'offline'` | LiveKit disconnects |
| Component unmount / route change | effect cleanup | LiveKit disconnects |

**The important non-case, stated deliberately:** a *transient* socket drop does **not** tear LiveKit down. `use-meeting.ts` listens for `connect_error`, not `disconnect`, so an established socket that blips leaves `state` at `admitted` while Socket.IO reconnects and re-emits `meeting:join-request`. That is exactly right — the seat is held for 30 s precisely so a blip does not cost you the room, and dropping video for it would be a regression. **Do not add a `disconnect` listener to `use-meeting.ts`.**
